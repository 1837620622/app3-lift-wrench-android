# 项目背景（请先读这一页）

> 本文是协作方与二次开发人员的**第一入口**。  
> 用正式、清楚的文字说明「为什么做这个 App」。细节需求、协议表、阶段计划见文末链接。

---

## 一句话

这不是要新造一把扳手，而是：**用厂家定制的工业扭矩扳手（Wi‑Fi + TCP/C 协议），在浮置板钢弹簧隔振器顶升/调频现场，把实时扭矩与转角采全、画清楚、能远程操控扳手、并导出带图的 Excel，先攒够几百～几千点数据；「平衡点/临界分离」算法是下一步，不是现在。**

---

## 再讲一遍（稍展开）

1. **业务对象**  
   轨道/浮置板下有很多**钢弹簧隔振器**。现场要顶升测力、调频（调整载荷/支承状态）。一台装置要服务**很多个隔振器、很多测点**，同一测点还要重复试验。

2. **工具从哪来**  
   扳手是**厂家定制/外购的工业设备**，不是本仓库的机械设计任务。手机 App 通过设备 Wi‑Fi 热点，用厂家 **TCP「C 协议」** 通信（根目录 `最新协议.docx`）。

3. **厂家做不到什么**  
   厂商扳手**不能可靠给出「平衡点」**（临界分离/原始支承力的工程结论）。协议里也**没有**现成的「平衡点」字段，只有扭矩、转角、结果状态等。

4. **我们现在做什么**  
   - 连上 Wi‑Fi + TCP 后：**读实时过程数据**（尤其 0x12 扭矩–转角），**可视化**到工人一眼能看懂；  
   - **远程控制扳手**（先开远程控制，再正转/反转/停止，可写参数、心跳、查 SN 等），做到「连上就能彻底按协议操控」；  
   - **全量入库**，导出 **带原生 Excel 图表** 的详细 `.xlsx`（CSV 可选），方便电脑里分析；  
   - 在**大量真实数据**（数百～数千点、多次试验）到位之前，**不宣称**已经能自动算准平衡点。

5. **下一步才做什么**  
   有足够数据与工况证据后：研发/验证「临界分离候选」算法，再**内嵌**进 App。在那之前，界面上最多是「待分析 / 候选参考」，禁止写成「已确认平衡」。

---

## 第三次强调（避免二次开发跑偏）

| 要做 | 不要做 |
| --- | --- |
| 协议忠实：收过程点、结果帧、状态；发远程控制与启停 | 改 CAD、造扳手硬件、改厂家帧格式「图省事」 |
| 横屏工业 UI：实时扭矩可视化、可读主图 | 把调试大面板当正式验收；正式 UI 出现「模拟采集」 |
| Wi‑Fi 优先 → TCP → 读数 + **安全的远程控制面板** | 把「结束采集/断开 App」说成机械已停 |
| 全量数据 + **原生 Excel 图**（扭矩–转角等） | 只导出最近 50 个显示点；把 CSV 改后缀冒充 xlsx |
| 先攒数据，算法 Phase 后置 | 未标定就输出正式力值；未验证就输出「平衡点已找到」 |

---

## 现场怎么用（目标流程）

打开 App（横屏）→ 填目标 Wi‑Fi / IP / 板号测点 → 系统里连上扳手 Wi‑Fi → TCP 连接 → **启用远程控制** → 按需正转顶升 / 反转 / 停止 → 看实时扭矩与曲线 → 结束本次会话并**导出带图 Excel** → 换测点或新建记录 → 多台/多次攒库 →（以后）算法内嵌。

## 交付次序（正式约定）

工业软件先落地、再传播，次序不可颠倒：

1. **先交付打磨完成的真实可运行界面（APK）**  
   横屏工人工作台、可读实时扭矩可视化、安全远程控制、带原生图表的 Excel 导出等，均以真机/模拟器渲染与现场可装包为准。不以概念图、宣传片代替验收。

2. **界面验收通过后，再制作高端宣传静帧与动态影像**  
   宣传物料必须**严格匹配已上线的实际界面**（布局、读数、曲线、控制区、导出结果），追求精致、顺滑、有质感的工业品牌表达。  
   **禁止**做成逐功能罗列的生硬演示片；动态以氛围与信任感为主，服务于推广，而不是操作说明书翻拍。

本仓库本轮只完成文档交接；**不在文档阶段生成宣传渲染或视频**。宣传制作单独立项，且不得倒逼尚未定稿的 UI。
